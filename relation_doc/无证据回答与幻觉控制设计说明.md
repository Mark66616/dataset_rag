# 无证据回答与幻觉控制设计说明

> 本文汇总《RAG_项目能力审计》中“无证据回答与幻觉控制”以及后续讨论形成的落地设计。本文所称“证据”是本次请求检索并经重排后、可定位到具体文档版本与位置的内容；模型参数知识、历史回答和未验证的推断均不构成证据。

## 1. 要解决的问题与目标

当前回答 Prompt 只要求模型“尽量基于参考内容，不要编造”。这属于软约束：当检索为空、候选弱相关、候选仅覆盖部分问题，或文档彼此冲突时，回答节点仍可能调用 LLM。结果是模型可能生成语气确定、但无法由知识库支持的内容；现有 API 也没有完整的结构化引用供用户核验。

本设计目标不是宣称完全消除幻觉，而是将风险变为可控制、可追溯、可度量的行为：

1. 无可靠证据时拒答或追问，且不调用回答 LLM；
2. 有证据时仅回答证据明确支持的部分；
3. 每项可验证的事实可定位到文档、版本、页码/章节和 chunk；
4. 文档冲突不被模型静默合并为一个确定结论；
5. 门控阈值由离线评测得到，并随模型、索引和数据变化重新验证。

## 2. 总体流程

```text
查询改写 / 实体确认
        ↓
多路检索 → RRF / 候选合并 → Reranker
        ↓
证据门控 node_evidence_gate
  ├─ 拒答：直接返回标准拒答
  ├─ 追问：直接返回澄清问题
  ├─ 部分回答：限定可回答要点
  └─ 可回答：携带编号证据进入生成
        ↓
node_answer_output（受限 Prompt 生成答案）
        ↓
引用完整性与事实支撑校验 node_citation_validate
  ├─ 通过：返回 answer + citations[]
  ├─ 可修复：最多一次受限重写
  └─ 失败：返回标准拒答/部分回答
```

建议将 `node_evidence_gate` 放在 `node_rerank` 与 `node_answer_output` 之间。若门控直接写入 `state["answer"]`，现有 `step_1_check_answer` 即可跳过生成调用；后续可将此行为改为更明确的 `evidence_decision` 状态字段。

## 3. 四层控制

| 阶段 | 是否调用回答 LLM | 核心职责 |
| --- | --- | --- |
| 生成前：证据门控 | 否（通常仅规则/小模型） | 判定证据是否足以回答、应拒答还是追问。 |
| 生成中：受限回答 | 是 | 仅按编号证据组织语言，并为事实添加引用。 |
| 生成后：确定性校验 | 否（通常） | 校验引用编号、引用元数据、关键数值及事实段覆盖。 |
| 修复：受限重写 | 可选，最多一次 | 删除或改写无引用内容；再次失败则拒答。 |

问题拆分可使用规则，复杂多意图问题也可使用一个 LLM 进行“问题规划”。该调用不产生事实答案，规划结果也不能视为证据；它只用于识别用户期望回答的要点。

### 3.1 生成前：证据门控

门控不应只判断 `reranked_docs` 是否非空，应综合以下条件：

- **候选有效性**：是否存在非空文本、状态为有效版本、具有可追溯元数据的候选；
- **直接支撑强度**：Top1 候选支撑核心结论的校准概率是否达到门槛；
- **问题要点覆盖率**：所有核心要点是否都有直接支撑；
- **来源规则**：产品规格、安全与维修类问题是否必须有本地受控知识库证据；Web 是否只能作补充；
- **版本和冲突**：候选是否存在不同有效版本的矛盾结论；是否可按发布日期/版本策略消解；
- **实体确定性**：产品型号是否已经确认，避免把相似型号的说明书当作证据。

门控结果建议结构化保存：

```json
{
  "decision": "answer | partial_answer | clarify | refuse",
  "reason_code": "NO_EVIDENCE | LOW_SUPPORT | INCOMPLETE_COVERAGE | ENTITY_AMBIGUOUS | CONFLICTING_EVIDENCE",
  "answerable_claim_ids": ["c-1", "c-3"],
  "evidence_ids": [1, 2],
  "gate_config_version": "gate-local-reranker-v1-2026-08-04"
}
```

`clarify` 与 `refuse` 不调用回答 LLM；`partial_answer` 仅允许模型回答 `answerable_claim_ids`，并强制说明未被资料支持的部分。

### 3.2 生成中：证据约束

上下文中的每一条证据须有稳定编号和来源元数据，例如：

```text
[1] source=local; document=HAK180 使用手册; version=v3; page=12;
chunk_id=hak180-v3-p12-c2
最大工作温度为 220℃。
```

Prompt 必须采用强约束，而不是“尽量”约束：

```text
只能使用编号证据中的信息回答。
每个可验证事实、数值、步骤和结论后必须标记 [编号]。
资料没有明确说明时，回答“提供的资料未说明，无法确认”。
不得使用模型常识补全，也不得将不同证据拼接为未被明确支持的结论。
若证据冲突，说明冲突及来源，不得自行裁决。
```

文档正文属于不可信数据，必须与系统/开发者指令清晰分隔；文档中的“忽略前述要求”等内容不得被当作指令执行。

### 3.3 生成后：引用与事实校验

第一期可使用确定性校验：

1. 回答是否包含引用；
2. 每个 `[n]` 是否对应本次允许使用的证据编号；
3. 是否存在没有引用的事实段、数值、型号、日期或操作步骤；
4. 引用是否包含可返回的 `document_id/version/page/section/chunk_id`；
5. 数值、型号、日期等关键字符串是否存在于被引用 chunk 中。

后续可为“句子—证据”加入 NLI/轻量验证模型，但不得将验证模型的自由文本判断作为唯一依据。校验失败时可让生成模型执行一次“仅保留能被下列证据直接支持的句子”的重写；仍失败则不输出原答案。

API 建议返回：

```json
{
  "decision": "answer",
  "answer": "最大工作温度为 220℃ [1]。",
  "citations": [
    {
      "index": 1,
      "document_id": "hak180_manual",
      "version": "v3",
      "page": 12,
      "section": "技术参数",
      "chunk_id": "hak180-v3-p12-c2"
    }
  ],
  "gate_config_version": "gate-local-reranker-v1-2026-08-04"
}
```

文档版本、`document_id`、对象键和版本切换的存储设计见同目录的 [文档版本存储设计](文档版本存储设计.md)。

## 4. 最低分阈值的离线校准

### 4.1 “已标注问题”是什么

“已标注问题”也称金标题或人工评测题。它不是只收集一批问题，而是为每题保存可人工核验的期望结果：

```json
{
  "id": "q-001",
  "question": "HAK180 的最大工作温度是多少？",
  "question_type": "single_fact",
  "risk_level": "high",
  "should_answer": true,
  "required_claims": [
    {
      "claim_id": "c-1",
      "description": "最大工作温度",
      "expected_answer": "220℃",
      "gold_evidence": [
        {
          "document_id": "hak180_manual",
          "version": "v3",
          "page": 12,
          "chunk_id": "hak180-v3-p12-c2"
        }
      ]
    }
  ]
}
```

无答案题也必须有：

```json
{
  "id": "q-002",
  "question": "HAK180 的无线协议版本是什么？",
  "question_type": "unanswerable",
  "risk_level": "high",
  "should_answer": false,
  "refusal_reason": "当前知识库未包含该信息"
}
```

每道题至少标明：是否应答、核心要点、正确证据位置、问题类型、风险级别；多要点题还需标注每个要点是否为必答项。理想情况下由两位业务人员独立标注，不一致时仲裁，以避免将个人经验误当作业务事实。

### 4.2 给每个候选打“证据标签”

仅有标准答案不足以校准 Reranker。对每道评测题运行当前完整检索链路，保存 Top-K 候选，并由人工逐条判定该候选能否支撑核心结论：

| 标签 | 含义 | 能否作为单事实答案依据 |
| --- | --- | --- |
| `direct_support` | 文本明确给出答案，或可无歧义推出答案 | 可以 |
| `partial_support` | 仅支持部分要点 | 仅可用于部分回答 |
| `related_but_insufficient` | 主题相近，但不能支撑所问结论 | 不可以 |
| `contradictory` | 与当前有效结论冲突 | 不可以直接放行 |
| `irrelevant` | 与问题无关 | 不可以 |
| `unsafe_or_untrusted` | 不可信来源或疑似注入内容 | 不可以 |

例如用户问“最大工作温度”，写有“推荐工作温度 110℃”的片段应标为 `related_but_insufficient`，绝不能因分数高就被视为“最大温度”的证据。

### 4.3 固定评测环境并切分数据

校准前记录并冻结：知识库快照、Embedding/Reranker 版本、Dense/Sparse 权重、Top-K、HyDE 开关、RRF 参数和 Web 策略。阈值只对这一套实际链路有效。

题集按“问题”而非按候选切为三部分，避免同一问题泄漏到不同集合：

```text
训练集：训练分数→概率的校准器（可选）
验证集：选择门控阈值和规则
测试集：阈值确定后仅用于最终验收
```

同一文档的高度相似问题也应尽量放在同一集合，避免评测只记住某篇文档的措辞和分数分布。

### 4.4 分析原始分数，不直接套用固定数字

原始 Reranker 分数没有跨模型通用含义。应统计验证集中每个分数区间的“直接支撑比例”：

| Top1 分数区间（示例） | `direct_support` 比例 |
| --- | --- |
| ≥ 8.5 | 99% |
| 8.0–8.5 | 94% |
| 7.0–8.0 | 71% |
| < 7.0 | 22% |

若业务目标是“被允许回答的问题中，至少 98% 有充分证据”，则在该模型、该知识库快照下，`8.5` 可以是候选阈值。它不是可复制给其他模型的通用数值。

可进一步用 Platt Scaling 或 Isotonic Regression 将原始分数转换为经验支撑概率：

```text
原始分数 8.7 → 支撑概率 0.97
原始分数 7.4 → 支撑概率 0.61
```

样本不足时，不应伪造精确概率；先按分数区间和人工复核确定较保守的阈值，并持续补充题集。

### 4.5 选择整套策略并在测试集验收

阈值不是单独的“Top1 ≥ T 就回答”。在验证集上组合并比较策略，例如：

```text
Top1 支撑概率：0.80 / 0.85 / 0.90 / 0.95
问题要点覆盖率：0.70 / 0.80 / 1.00
产品规格是否必须有本地证据：是 / 否
高风险题是否允许部分回答：是 / 否
```

对每组策略计算：错误放行率、错误拒答率、正确回答率、拒答率、高风险题错误放行率和引用完整率。选择满足安全目标后正确回答率最高的规则，并只在未参与选参的测试集上报告最终结果。

发布时使用版本化配置，而不是将阈值硬编码：

```yaml
evidence_gate:
  config_version: gate-local-reranker-v1-2026-08-04
  retrieval_bundle: bge-m3__reranker-v1__kb-snapshot-20260804
  local_min_support_probability: 0.90
  web_min_support_probability: 0.95
  normal_coverage: 0.80
  high_risk_coverage: 1.00
  require_local_evidence_for_product_specs: true
  max_repair_attempts: 1
```

每次请求记录实际使用的链路、配置版本、Top1 分数、校准概率、覆盖率、门控决定和拒答原因。模型、Reranker、检索策略、知识库大版本或来源策略变化后，应重新运行评测并发布新配置；不是每次用户提问时重新校准。

## 5. 覆盖率与分数差的正确使用

### 5.1 问题要点覆盖率

覆盖率按“用户问题需要的结论”计算，不按“召回了几篇文档”计算。例如：

```text
问题：最大温度、推荐温度和故障排查步骤是什么？
要点 1：最大温度，权重 0.4，必答
要点 2：推荐温度，权重 0.2，非必答
要点 3：故障排查步骤，权重 0.4，必答
```

只有找到 `direct_support` 证据的要点才计入：

```text
coverage = 已覆盖要点权重之和 / 全部要点权重之和
```

若资料仅支持要点 2 和 3，覆盖率为 60%，但要点 1 是必答项。此时不能回答“最大温度是多少”；可回答已覆盖部分并清楚声明“资料未说明最大工作温度，无法确认”。高风险问题一般要求所有必答项覆盖，通常取 100%。

### 5.2 Top1/Top2 分差

分差适合用于产品型号等实体消歧：

```text
HAK180：0.83
HAK-180 Pro：0.82
```

这代表型号不确定，应该反问用户。对文档重排不能把“小分差”直接视为低质量：两篇高分文档分数接近往往意味着相互支持。文档证据门控主要使用“Top1 支撑概率、覆盖率、版本/来源冲突”；仅当候选整体低分且接近时，才可作为无可靠证据的辅助信号。

## 6. 金标题覆盖范围

人工金标题不需要覆盖知识库每一份文档，但也不能只覆盖热门、格式干净的文档。应分两层：

| 层级 | 范围 | 目的 |
| --- | --- | --- |
| 全量自动检查 | 所有入库文档 | 验证解析、chunk、索引写入、元数据、版本与删除是否正确。 |
| 人工金标题 | 分层抽样的代表性问题/文档 | 校准门控、验证检索质量、忠实性和拒答能力。 |

人工题优先覆盖高频手册、FAQ、故障处理文档，高风险的安全/维修/参数资料，以及每个产品线、文档类型、版本、长度和多模态形式。还应独立构造无答案、歧义、冲突版本等负例。核心或高风险文档可每份准备 3～10 道金标题；普通文档按产品线、类型、长度和版本分层抽样。

所有文档至少要自动验证：成功解析、存在有效 chunk、写入向量库、保留 `document_id/version/page/title/chunk_id`、可通过基础标题/关键词召回，以及更新/删除后旧版本不会错误被召回。新增高风险文档时新增人工题；更新文档时重跑其相关题和冲突版本题；模型或策略改动时运行完整固定回归集。

## 7. 主模型与兜底模型

配置应区分“证据链路”和“回答链路”：

```text
Embedding + Reranker + 索引快照 + 来源策略
    → 证据门控配置

回答 LLM + Prompt + 引用校验器
    → 生成与引用校验配置
```

| 兜底变化 | 是否需重新校准证据阈值 | 额外要求 |
| --- | --- | --- |
| 仅回答 LLM 变化 | 通常不需要，前提是检索/Reranker 不变 | 单独运行端到端忠实性、引用完整率、拒答遵从率与注入防护评测。 |
| Reranker 变化 | 必须需要 | 原始分数尺度不同，旧阈值无效。 |
| Embedding/检索策略变化 | 必须需要 | 候选分布、覆盖率和重排分数均会改变。 |
| Web 来源策略变化 | 建议需要 | 可信度、噪声与时效性发生改变。 |
| 知识库大版本更新 | 建议重新验证 | 新文档和版本冲突会改变实际证据质量。 |

若兜底回答 LLM 忠实性较差，可使用更严格的生成策略，例如提高最低支撑概率、要求每个事实有引用、强制启用生成后校验，并限制为最多一次修复重写。

## 8. 分阶段实施与验收

### 第一阶段：最小可用控制

1. 在重排后新增 `node_evidence_gate`；
2. 对空候选、无有效版本、低于保守阈值的候选直接拒答；
3. 改写回答 Prompt，要求按编号证据回答并引用；
4. API 返回 `decision`、`reason_code` 与基础 `citations[]`；
5. 记录门控日志和所有拒答原因。

验收：空召回不调用回答 LLM；低分候选不产生确定性答案；放行答案能返回至少一个有效引用。

### 第二阶段：可度量校准

1. 构建首批金标题和候选证据标签；
2. 固定评测快照，计算最低分、覆盖率与来源规则的效果；
3. 选择并发布版本化门控配置；
4. 运行未参与选参的测试集；
5. 增加引用完整性与关键数值校验。

验收：可报告错误放行率、错误拒答率、拒答率、引用完整率；阈值可以追溯至评测集和配置版本。

### 第三阶段：持续治理

1. 将评测集、门控配置和链路版本接入 CI/定时回归；
2. 按高风险、长尾和新增文档扩充题集；
3. 模型或检索链路变更时强制重新评测；
4. 对冲突证据、Web 证据和 Prompt Injection 增加专项测试；
5. 基于线上人工纠错和抽样复核迭代题集。

验收：质量低于已发布基线时阻止发布；每个线上回答可定位其证据链路与门控决定。
